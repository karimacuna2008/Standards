🔀 Git Workflow

Cómo gestionar ramas, commits, merges y versiones en todos los proyectos

¿Qué es?

El estándar de Git Workflow define las reglas para trabajar con control de versiones: cómo nombrar commits, cómo crear y gestionar ramas, cómo hacer merges y cómo versionar releases. Es el protocolo que Claude propone cuando trabaja con git en cualquier proyecto.

Un detalle importante: Claude propone los comandos, el usuario los ejecuta. Claude no corre git commit, git push ni ningún comando que modifique el historial — eso es responsabilidad exclusiva del usuario.

Sin AI en el historial: Claude nunca agrega trailers de co-autoría (Co-Authored-By) ni firma commits como asistente. El historial debe leerse como completamente de autoría humana.

¿Para qué sirve?

  • Trazabilidad: Los Conventional Commits hacen que el historial sea legible por humanos y por herramientas. Se puede entender qué cambió, por qué y en qué área con solo leer el mensaje.
  • Aislamiento de trabajo: El modelo de ramas (feature/fix → develop → main) garantiza que el código en desarrollo no rompa lo que está en producción.
  • Releases limpios: El Semantic Versioning comunica con precisión qué tipo de cambios trae cada versión — sin ambigüedades para el equipo o los usuarios.
  • Reversibilidad: Al tener main siempre estable, un problema en develop nunca contamina el código de producción.
  • Colaboración predecible: Cuando todos siguen las mismas reglas de naming y merging, el trabajo conjunto se vuelve mecánico — no hace falta adivinar qué hizo cada rama.

¿Por qué este enfoque?

Los Conventional Commits se eligieron porque son el estándar de la industria más adoptado, permiten generar CHANGELOGs automáticamente, y son legibles tanto por personas como por herramientas de CI/CD.

El modelo de tres ramas (main / develop / feature) es una versión simplificada de Gitflow. No usa release/ ni hotfix/ porque añaden complejidad sin beneficio claro en proyectos personales o pequeños equipos.

El squash merge de features a develop mantiene el historial lineal y limpio. Cada feature se convierte en un único commit significativo — no en una secuencia de "fix", "fix2", "wip" que solo tiene sentido para quien trabajó en esa rama.

El Semantic Versioning (MAJOR.MINOR.PATCH) es el contrato más extendido para comunicar cambios: cualquier desarrollador entiende qué significa pasar de v1.2.3 a v2.0.0 sin leer el código.

No se requieren herramientas externas más allá de git. Los mensajes de commit son texto plano con una convención específica.

Cómo aplicarlo

1. Mensajes de commit — Conventional Commits

Cada commit sigue el formato:

type(scope): description # Ejemplos: feat(auth): add user login validation fix(api): handle null response in fetch docs(readme): update installation instructions refactor(database): extract connection logic to module test(auth): add unit tests for token validation chore(deps): update requests to 2.31.0

Los tipos disponibles:

TipoCuándo usarlo
featNueva funcionalidad para el usuario
fixCorrección de un bug
docsCambios solo en documentación
styleFormato, espacios, punto y coma (sin cambio de lógica)
refactorReestructuración de código sin cambiar comportamiento
testAgregar o corregir tests
choreTareas de mantenimiento (deps, config, scripts)

Reglas del mensaje:

  • La descripción va en minúsculas e imperativo: "add" no "added", "fix" no "fixed"
  • El scope es el área afectada: auth, api, database, ui, etc.
  • Máximo ~72 caracteres en la primera línea
  • Puedes agregar un cuerpo con más contexto separado por una línea en blanco

2. Modelo de ramas

main ──────────────────────────────────────────● v1.1.0 ↑ develop ──────────●──────────────────────────────● squash merge ↑ ↑ feature/login ─────● (terminada) feature/dashboard ─────●
RamaPropósitoRegla
mainCódigo estable, listo para producciónSolo recibe merges desde develop, en releases
developIntegración; todas las features van aquí primeroSiempre debe estar en estado "funcional"
feature/*Una feature o mejora específicaBranch off develop · eliminar después del merge
fix/*Un bug específicoBranch off develop · eliminar después del merge

Naming de ramas: feature/user-login, feature/export-csv, fix/email-validation, fix/null-pointer-api

3. Merging

  • feature → develop: squash merge. Toda la feature queda como un único commit con mensaje Conventional Commits.
  • develop → main: merge en cada release. El squash es opcional — un commit por release es suficiente.
  • Una sola feature o fix por rama. Las ramas mixtas son difíciles de revertir y de code-review.

4. Tags — Semantic Versioning

Las versiones siguen el formato vMAJOR.MINOR.PATCH:

CambioQué incrementaEjemplo
Primer release—v1.0.0
Nueva funcionalidad (compatible)MINORv1.0.0 → v1.1.0
Solo bug fixesPATCHv1.1.0 → v1.1.1
Cambio que rompe compatibilidadMAJORv1.1.1 → v2.0.0

Los tags van en main después de cada release merge.
