📚 Documentation

Qué documentación crear, qué incluir en cada archivo y cuándo hacerlo

¿Qué es?

El estándar de Documentation define qué archivos de documentación debe tener cada proyecto, qué secciones incluir en cada uno, y cuándo crearlos. Cubre tres niveles: el README en la raíz, el CHANGELOG para releases, y la carpeta /docs para proyectos más complejos.

Los docstrings y comentarios de código son parte de este ecosistema pero se tratan en sus propios estándares: python/code-standards.md y python/functions.md.

Este estándar es transversal — aplica a todos los proyectos independientemente del lenguaje o tipo. El nivel de detalle se ajusta al tamaño del proyecto, pero el README siempre existe.

¿Para qué sirve?

  • Onboarding instantáneo: Un buen README hace que alguien pueda entender, instalar y correr el proyecto sin preguntar nada. Incluyendo tú mismo después de 3 meses sin tocarlo.
  • Trazabilidad de cambios: El CHANGELOG es el historial legible por personas de qué cambió en cada versión — más accesible que el git log.
  • Referencia técnica: La carpeta /docs guarda la información que no cabe en el README: endpoints de API, arquitectura, esquemas de BD, guías de deployment.
  • Consistencia: Cuando todos los proyectos tienen la misma estructura de documentación, navegar entre proyectos es predecible.
  • Reduces dependencia de memoria: La documentación externaliza el conocimiento que de otro modo vive solo en la cabeza del desarrollador.

¿Por qué este enfoque?

La estructura del README está ordenada por lo que un nuevo usuario necesita saber: primero entiende qué es, luego cómo instalarlo, luego cómo usarlo. Las secciones más técnicas (arquitectura, troubleshooting) van al final porque son para usuarios avanzados.

El CHANGELOG sigue el formato Keep a Changelog (keepachangelog.com) porque es el estándar más adoptado. Agrupar cambios en categorías fijas (Added, Changed, Fixed, Removed) hace que el lector encuentre lo que busca sin leer todo.

La regla de "crear /docs solo para APIs, librerías y proyectos grandes" evita el overhead de mantener documentación que nadie leerá en proyectos pequeños. La documentación que no se actualiza es peor que no tener documentación.

Con qué

Markdown (.md) README.md CHANGELOG.md /docs

Toda la documentación se escribe en Markdown. No se requieren herramientas externas — GitHub, GitLab y VS Code lo renderizan automáticamente.

Cómo aplicarlo

1. README.md — siempre requerido

Todo proyecto tiene un README.md en la raíz. Las secciones se incluyen en este orden; omitir las que no apliquen:

  1. 1.Title + description — Una línea de qué hace el proyecto, seguida de un párrafo corto sobre el problema que resuelve.
  2. 2.Features — Lista de bullet points con las funcionalidades principales.
  3. 3.Installation — Prerrequisitos primero (versiones de Python/Node/etc.), luego los pasos: clone → venv → install → config.
  4. 4.Usage — Un ejemplo mínimo ejecutable. Casos de uso comunes. Invocación desde CLI si aplica.
  5. 5.Configuration — Variables de entorno y claves de config-file. Una línea por variable: nombre y propósito.
  6. 6.Architecturesolo proyectos medianos/grandes — Componentes, flujo de datos, decisiones de diseño clave.
  7. 7.Testing — Cómo correr los tests, si los hay.
  8. 8.Troubleshooting — Errores comunes como tabla Issue → Solution.

Skeleton de README

# Nombre del Proyecto Una línea de descripción. ## Features - ... ## Installation ### Prerequisites - Python 3.10+ ### Steps ```bash git clone https://github.com/... cd proyecto python -m venv venv venv\Scripts\activate # Windows pip install -r requirements.txt cp .env.example .env # editar con tus valores ``` ## Usage ```bash python main.py ``` ## Configuration - `API_KEY` — clave para autenticación con la API externa - `DEBUG_MODE` — activa logs detallados (True/False) ## Testing ```bash pytest ```

2. CHANGELOG.md — requerido cuando hay releases

Va en la raíz. La entrada más reciente arriba. Una entrada por release con este formato:

## [1.2.0] - 2026-05-31 ### Added - Export to CSV with custom delimiter option - Progress bar for long-running operations ### Changed - Improved error messages in API client (now include endpoint and status code) ### Fixed - Null pointer when API returns empty response on /users endpoint ### Removed - Deprecated `--legacy` flag (removed after 6-month deprecation period) --- ## [1.1.1] - 2026-05-15 ### Fixed - Timeout not applying to retry attempts in fetch_with_retry()

Las categorías disponibles son: Added, Changed, Fixed, Removed, Deprecated. Omite las que no aplican en esa release. El lenguaje es orientado al usuario, no a la implementación.

3. Carpeta /docs — solo cuando aplica

Cuándo crear /docs: APIs, librerías reutilizables, y proyectos medianos/grandes con múltiples módulos. No crearla para scripts simples, utilidades pequeñas y herramientas internas de uso ocasional.

Cuando /docs existe, los archivos típicos son:

ArchivoContenido
installation.mdGuía detallada de instalación (desarrollo y producción)
architecture.mdComponentes, diagramas, decisiones de diseño, flujo de datos
api.mdReferencia de endpoints: método, path, request, response, códigos de error
configuration.mdTodas las variables de entorno y opciones de config explicadas en detalle
deployment.mdPasos para deploy en producción, variables de entorno de prod, rollback
troubleshooting.mdErrores conocidos, diagnóstico, soluciones probadas
