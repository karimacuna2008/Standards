⚙️ Python Functions

Cómo nombrar, tipear, documentar y presentar funciones en Python

¿Qué es?

El estándar de Functions define cómo Claude escribe y presenta funciones en proyectos Python: la convención de nombres, el uso de type hints, el formato de docstrings, y el proceso de explicación técnica profunda en el chat cuando presenta una función nueva.

Existe un principio fundamental en este estándar: Claude pregunta antes de crear funciones auxiliares (helper functions). No extrae código a una función separada por decisión propia — eso es decisión del usuario.

¿Para qué sirve?

  • Autoexplicación: Un nombre bien elegido hace que no necesites comentarios para entender qué hace la función. fetch_user_by_id() es completamente evidente; get_data() no dice nada.
  • Detección temprana de bugs: Los type hints permiten que los IDEs y linters detecten errores de tipo antes de ejecutar el código.
  • Documentación en el punto de uso: Los docstrings aparecen en el autocompletado del IDE — el desarrollador entiende la función sin abrir el archivo donde está definida.
  • Comprensión profunda: El desglose técnico en el chat (parámetros, retorno, lógica interna, variables) asegura que el usuario entiende exactamente qué va a ejecutar antes de ejecutarlo.
  • Control de refactoring: La regla de "preguntar antes de extraer helpers" previene que Claude reestructure código sin el consentimiento del usuario.

¿Por qué este enfoque?

Verb + Noun naming: Las funciones son acciones — hacen algo. Nombrarlas como verbo+sustantivo (fetch_user, calculate_total) describe exactamente qué acción realizan sobre qué entidad. Los nombres genéricos (process, handle, do_stuff) son señales de que la función hace demasiadas cosas.

Type hints obligatorios: Python es dinámicamente tipado, pero eso no significa que el código deba ser opaco. Los type hints convierten el código en documentación ejecutable — el lector sabe qué recibe y qué devuelve sin ejecutarlo.

Google style docstrings: El estilo de Google es el más legible para lectura directa en el código. Es más explícito que los NumPy docstrings para proyectos no científicos y más estructurado que los docstrings de una sola línea para funciones de más de 2 parámetros.

Preguntar antes de extraer helpers: La extracción de código a funciones auxiliares es una decisión de diseño con implicaciones en testabilidad, legibilidad y arquitectura. No es una refactorización automática — el usuario decide si es necesaria.

Con qué

Python 3.6+ typing (Union, Optional, List...) Google style docstrings

No se requieren librerías externas. El módulo typing de la stdlib provee los tipos necesarios. A partir de Python 3.10 se puede usar X | Y directamente en vez de Union[X, Y].

Cómo aplicarlo

1. Naming — Verbo + Sustantivo

El nombre comunica la acción (verbo) y sobre qué (sustantivo). Cada verbo tiene un significado preciso:

VerboCuándo usarloAlternativas
fetch_Obtener datos de API o BDload_ (archivos), get_ (acceso simple)
transform_Cambiar forma o formato de datosparse_ (string → estructura)
validate_Verificar que algo es válidois_valid_ (si retorna bool)
create_Instanciar o persistir un objeto nuevobuild_ (construcción compleja)
delete_Eliminar de BD o persistenciaremove_ (de colecciones), clean_ (limpieza)
# ✅ Nombres claros def fetch_user(user_id: int) -> dict: ... def validate_email(email: str) -> bool: ... def transform_orders(raw_orders: list[dict]) -> list[dict]: ... def create_report(data: list[dict], title: str) -> str: ... # ❌ Nombres genéricos — no dicen nada def process(data): ... def handle_stuff(x): ... def do_operation(input): ...

2. Type Hints — requeridos (con excepciones)

# ✅ Obligatorio en toda función def fetch_user(user_id: int) -> dict: """Retrieve user data from API.""" def validate_email(email: str) -> bool: """Check if email format is valid.""" # Tipos complejos def process_orders(orders: list[dict], min_amount: float = 0) -> list[dict]: ... # Múltiples tipos posibles def parse_id(value: str | int) -> int: ... # Puede retornar None def find_user(email: str) -> dict | None: ... # ✅ No necesitan type hints (triviales) for i in range(10): x = i + 1 # obvio del contexto

3. Docstrings — Google Style

def process_orders(orders: list[dict], min_amount: float = 0) -> list[dict]: """Filter orders by minimum amount and format prices. Args: orders: List of order dicts with 'amount' and 'status' keys. min_amount: Minimum order amount to include. Default: 0 (include all). Returns: List of filtered orders with 'formatted_price' field added. Note: Returns empty list if no orders meet the criteria. """
  • Primera línea: resumen en imperativo (Filter, no Filters)
  • Sección Args: todos los parámetros con descripción concisa
  • Sección Returns: qué devuelve y en qué formato
  • Sección Note: casos especiales, si los hay
  • Funciones de una sola línea obvias pueden tener solo el resumen de una línea

4. Desglose técnico profundo — en el chat

Cuando Claude presenta una función nueva, la explica en el chat con este nivel de detalle (no en el docstring):

Esta función filtra órdenes y les agrega precio formateado. Parámetros: - orders: Lista de dicts con claves 'amount' (float) y 'status' (str) - min_amount: Umbral de filtro — incluye todo si es 0 (valor por defecto) Retorna: Lista de dicts con los campos originales + nuevo campo 'formatted_price' (str) Lógica interna: - Itera sobre orders, filtra por amount >= min_amount - Crea filtered_orders como lista intermedia de almacenamiento - Aplica formato de moneda al amount de cada orden - Retorna lista vacía si no hay coincidencias (manejado con gracia) Variables creadas: - filtered_orders: guarda las órdenes que pasan el umbral - result: lista final con precios formateados

5. Tamaño y parámetros

No hay límites fijos. La guía es:

  • Cada función hace un trabajo principal (responsabilidad única)
  • Si el cuerpo de la función salta entre 3+ tareas distintas, considerar dividirla
  • Si hay muchos parámetros y la lógica se vuelve confusa, considerar agrupar en dataclass
  • El tamaño correcto es "tan larga como necesite ser para ser clara"

6. Helpers — preguntar antes de crear

Regla: Claude pregunta antes de extraer código a una función auxiliar. No lo hace automáticamente. El usuario decide basándose en: ¿se reutilizará? ¿mejora la claridad? ¿es una unidad testeable?
