🛡️ Python Error Handling

Cómo manejar errores, excepciones y fallos en Python: cuándo absorber, cuándo lanzar, y cómo limpiar recursos

¿Qué es?

El estándar de Error Handling define el control de flujo ante fallos: qué hacer cuando algo sale mal en diferentes partes del código. Cubre tres jerarquías de respuesta según la severidad, la decisión de absorber vs relanzar excepciones, validación de variables de entorno, manejo de archivos externos, excepciones personalizadas, encadenamiento de excepciones, limpieza de recursos, y la diferencia entre logging.exception() y logging.error().

La mecánica de logging (configurar handlers, niveles, formatos) está en python/observability.md (pendiente). Este estándar solo define qué nivel de logging usar ante cada tipo de error.

¿Para qué sirve?

  • Evita errores silenciosos: Absorber una excepción con except: pass es una de las causas más difíciles de diagnosticar — el código falla en otro lugar y no hay rastro de dónde empezó el problema.
  • Proporcionalidad: No todos los errores son iguales. Un campo opcional faltante no merece matar el script; una configuración inválida sí.
  • Tracebacks preservados: El encadenamiento de excepciones (raise X from e) asegura que el traceback original no se pierda al re-lanzar con otro tipo de excepción.
  • Recursos siempre liberados: Los context managers y finally garantizan que archivos, conexiones y temporales se cierren incluso cuando hay errores.
  • Diagnóstico rápido: Saber qué nivel de logging usar (exception vs error) hace que los tracebacks aparezcan cuando los necesitas y no cuando añaden ruido.

¿Por qué este enfoque?

Jerarquía de 3 niveles: La respuesta ante un error debe ser proporcional a su gravedad. Un script que usa sys.exit(1) para todo es tan malo como uno que ignora todo con pass — ambos extremos son inutilizables. La jerarquía provee un marco de decisión claro.

Validar env vars al inicio, todas juntas: Fallar lo antes posible (fail-fast) es una práctica de ingeniería fundamental. Descubrir que falta SECRET_TOKEN después de 2 minutos de procesamiento es peor que descubrirlo al arrancar. Reportar todas las variables faltantes juntas ahorra un ciclo de fix-run-fail por variable.

raise X from e (exception chaining): Cuando conviertes un JSONDecodeError en un ConfigError, perder el traceback del JSON hace el debugging imposible. Con from e ambos errores aparecen en el traceback — el original y el nuevo.

Excepciones específicas: Las excepciones built-in genéricas (Exception) capturan todo — incluidos KeyboardInterrupt y SystemExit. Excepciones específicas hacen que el except capture exactamente lo que esperas, no más.

Con qué

try/except (builtin) sys (stdlib) logging (stdlib) contextlib (stdlib) json (stdlib)

Todo de la stdlib. No se requieren librerías externas para manejo de errores básico.

Cómo aplicarlo

1. Jerarquía de respuesta — 3 niveles

NivelCuándoRespuesta
Nivel 1Error menor, el proceso puede continuarprint + continue / skip
Nivel 2Operación falló, el caller decide qué hacerreturn None o raise una excepción
Nivel 3Config inválida, credencial faltante, fallo irrecuperablesys.exit(1)
# Nivel 1 — error menor, el script continúa for user in users: if not user.get('email'): print(f" ⚠️ User {user['id']} has no email — skipping") continue # Nivel 2 — operación fallida, el caller maneja def process_file(path: str) -> dict | None: if not os.path.exists(path): print(f" ✗ File not found: {path}") return None # Nivel 3 — error fatal en inicialización def main(): if not API_KEY: print(" ✗ API_KEY not set — cannot continue") sys.exit(1)

2. Absorber vs Relanzar (Raise vs Absorb)

# ✅ ABSORBER — cuando puedes manejar el error completamente aquí def get_user_age(user: dict) -> int: try: return int(user['age']) except (KeyError, ValueError): return 0 # valor por defecto; el caller no necesita saber # ✅ RELANZAR — cuando el caller necesita saber que falló def load_config(path: str) -> dict: try: with open(path, encoding='utf-8') as f: return json.load(f) except FileNotFoundError: raise # el caller decide qué hacer si no hay config # ❌ ABSORBER SIN ACCIÓN — el peor caso: error silencioso def load_config(path: str) -> dict: try: with open(path, encoding='utf-8') as f: return json.load(f) except FileNotFoundError: pass # ¿qué retorna? ¿qué sabe el caller? Nada.

Regla: si absorbes, siempre hay una acción: loguear, retornar un default, o imprimir. Nunca absorber en silencio (except: pass).

3. Validar variables de entorno al inicio

import os, sys from dotenv import load_dotenv def validate_env() -> None: """Verificar que todas las variables requeridas están configuradas.""" load_dotenv() required = ['API_KEY', 'DATABASE_URL', 'SECRET_TOKEN'] missing = [var for var in required if not os.getenv(var)] if missing: print(f" ✗ Missing required environment variables: {', '.join(missing)}") sys.exit(1) def main(): validate_env() # siempre primero # resto del script...
  • Función dedicada validate_env() — no inline en main()
  • Validar todas las variables juntas en un solo mensaje
  • sys.exit(1) inmediato si falta alguna — nunca continuar con None
  • Primera llamada en main(), antes de cualquier otra inicialización

4. Archivos externos — qué excepciones capturar

# Cualquier archivo de texto (.txt, .log, .md, etc.) try: with open(path, encoding='utf-8') as f: content = f.read() except FileNotFoundError: print(f" ✗ File not found: {path}") sys.exit(1) # JSON — agregar JSONDecodeError (puede existir pero estar corrupto) try: with open(path, encoding='utf-8') as f: data = json.load(f) except FileNotFoundError: print(f" ✗ File not found: {path}") sys.exit(1) except json.JSONDecodeError as e: print(f" ✗ Invalid JSON in {path}: {e}") sys.exit(1) # CSV — FileNotFoundError es suficiente try: with open(path, encoding='utf-8') as f: data = list(csv.DictReader(f)) except FileNotFoundError: print(f" ✗ File not found: {path}") sys.exit(1)

Siempre incluir el path en el mensaje de error. Siempre encoding='utf-8' explícito. Para XML, YAML, TOML: agregar el parser error específico de ese formato.

5. Excepciones personalizadas

# ✅ Usar built-ins para errores genéricos raise ValueError("Invalid email format") raise TypeError("Expected string, got int") raise KeyError("Required key 'user_id' not found") # ✅ Crear excepciones propias cuando el caller necesita capturarlas por tipo class ConfigError(Exception): """Raised when configuration is missing or invalid.""" pass class APIAuthError(Exception): """Raised when API credentials are invalid or expired.""" pass # El caller puede capturar solo ese tipo específico try: load_config('config.json') except ConfigError as e: print(f" ✗ Configuration problem: {e}") sys.exit(1)

Nombre siempre termina en Error. Heredar de Exception, no de BaseException. Definir al top del módulo o en un exceptions.py si hay varias.

6. Encadenamiento de excepciones — raise X from e

# ✅ Preserva el traceback original def load_config(path: str) -> dict: try: with open(path, encoding='utf-8') as f: return json.load(f) except json.JSONDecodeError as e: raise ConfigError(f"Config file is corrupted: {path}") from e # Traceback muestra: JSONDecodeError (causa) + ConfigError (resultado) # ❌ Pierde el traceback original def load_config(path: str) -> dict: try: with open(path, encoding='utf-8') as f: return json.load(f) except json.JSONDecodeError: raise ConfigError(f"Config file is corrupted: {path}") # Solo muestra ConfigError — no sabes en qué línea falló el JSON

Suprimir el original explícitamente cuando es intencional: raise ConfigError(...) from None.

7. Limpieza de recursos — with vs finally

# ✅ Context manager — preferido cuando el objeto lo soporta with open('data.json', encoding='utf-8') as f: data = json.load(f) # f.close() es automático # ✅ Múltiples recursos en una línea with open('input.csv', encoding='utf-8') as fin, open('output.csv', 'w') as fout: pass # ✅ finally — para cleanup sin context manager temp_path = create_temp_file() try: process(temp_path) finally: os.remove(temp_path) # siempre se elimina, incluso si process() falla

8. logging.exception() vs logging.error()

import logging try: result = int("abc") except ValueError as e: # logging.error() — solo el mensaje logging.error(f"Conversion failed: {e}") # Output: ERROR - Conversion failed: invalid literal... # logging.exception() — mensaje + traceback completo logging.exception(f"Conversion failed: {e}") # Output: ERROR - Conversion failed... # Traceback (most recent call last): # File "script.py", line 2 ... # ValueError: invalid literal for int()...
SituaciónUsar
Dentro de un bloque except y quieres el tracebacklogging.exception()
Fuera de except, o el traceback no aporta contextologging.error()
Errores esperados y controlados (input inválido del usuario)logging.warning()

Dentro de un except, usar logging.exception() por defecto — el traceback no cuesta nada y ayuda enormemente al debugging.
