🎨 Python Code Standards

Convenciones de estilo, estructura y organización para escribir Python consistente y legible

¿Qué es?

El estándar de Code Standards define las convenciones de escritura de Python que Claude aplica en todos los proyectos: cómo nombrar variables, funciones, clases y constantes; cómo organizar los imports; qué largo máximo tienen las líneas; cuándo usar f-strings; y cómo estructurar el código según el tipo de proyecto.

La base es PEP 8 con una sola modificación: el límite de línea es 120 caracteres en vez de 79. El resto de PEP 8 aplica sin excepciones.

¿Para qué sirve?

  • Legibilidad predecible: Cuando todos los proyectos siguen las mismas convenciones, cambiar de uno a otro no requiere adaptación. El código se lee, no se descifra.
  • Reduce errores por ambigüedad: Naming conventions claras (snake_case, UPPER_CASE, PascalCase) hacen evidente qué tipo de cosa es cada identificador sin tener que leer su definición.
  • Facilita el code review: Las convenciones comunes eliminan discusiones subjetivas de estilo — el estándar es el árbitro.
  • Compatibilidad con herramientas: PEP 8 + f-strings + imports organizados son los patrones que los linters (flake8, pylint) y formateadores (black, ruff) esperan por defecto.

¿Por qué este enfoque?

120 caracteres en vez de 79: El límite original de PEP 8 venía de terminales de 80 columnas de los años 70. Los monitores modernos son más anchos. 120 caracteres permite escribir código más legible sin tener que partirlo artificialmente en múltiples líneas.

F-strings siempre: Son la forma más clara, rápida y legible de formatear strings en Python moderno (3.6+). No hay razón para usar .format() o % en código nuevo.

Imports en 3 grupos: La separación stdlib → third-party → local permite ver de un vistazo qué depende de Python estándar, qué instalaste con pip, y qué es tuyo. Facilita mover el código a otro entorno.

config.py para constantes: Las constantes de configuración en un archivo dedicado son fáciles de encontrar, modificar y no contaminar el código de negocio con valores hardcoded.

Con qué

Python 3.6+ PEP 8 flake8 / ruff (linter opcional) black (formatter opcional)

No se requiere ningún linter específico, pero estas herramientas validan automáticamente la mayoría de las reglas de este estándar si se quieren usar.

Cómo aplicarlo

1. Estructura de proyecto

La estructura depende del tipo de proyecto. Empezar simple y expandir si el proyecto crece:

Scripts / Herramientas pequeñas

proyecto/ ├─ main.py ├─ utils.py ├─ config.py ├─ requirements.txt └─ README.md

Data Science / Análisis

proyecto/ ├─ notebooks/ │ └─ 01_exploration.ipynb ├─ data/ │ ├─ raw/ │ └─ processed/ ├─ scripts/ └─ requirements.txt
# Proyectos medianos / grandes proyecto/ ├─ src/ │ ├─ module1/ │ │ ├─ __init__.py │ │ └─ core.py │ └─ config.py ├─ tests/ ├─ requirements.txt └─ README.md

2. Imports — 3 grupos, orden alfabético

# 1. Standard library import os import sys from pathlib import Path from datetime import datetime # 2. Third-party (instalados con pip) import requests import pandas as pd import numpy as np # 3. Locales (propios del proyecto) from utils import helper_function, process_data from config import API_KEY, DEBUG_MODE
  • Un grupo por categoría, separados por una línea en blanco
  • Orden alfabético dentro de cada grupo
  • Imports específicos siempre — nunca from module import *

3. Naming conventions

TipoConvenciónEjemplo
Variables y funcionessnake_caseuser_name, process_data()
ConstantesUPPER_CASEAPI_KEY, MAX_RETRIES
ClasesPascalCaseUserManager, DataProcessor
Métodos/atributos privados_underscore_prefix_validate_email(), _internal_data

El prefijo _ en métodos y atributos privados es una señal de "implementación interna — no usar desde fuera". Python no lo bloquea técnicamente, pero es una convención que todos respetan.

4. F-strings para formateo

# ✅ Siempre f-strings name = "Ana" age = 30 message = f"Nombre: {name}, Edad: {age}" total = f"Total: {price * quantity}" formatted = f"Valor: {number:.2f}" # 2 decimales # ❌ No usar .format() ni % message = "Nombre: {}, Edad: {}".format(name, age) # evitar message = "Nombre: %s, Edad: %d" % (name, age) # evitar

5. Longitud de línea — 120 caracteres

# ✅ Bien (bajo 120 caracteres) result = long_function_name(arg1, arg2, arg3) if condition else default_value # ❌ Demasiado largo (over 120) result = very_long_function_name_unnecessarily_verbose(argument_one, argument_two, argument_three, argument_four) # ✅ Partir si es necesario result = ( very_long_function_name(arg1, arg2, arg3) if condition else default_value )

6. Comentarios — solo el POR QUÉ

# ✅ Bueno — explica el POR QUÉ, no el QUÉ def calculate_discount(price, customer_type): # VIP customers get 15% discount (business rule from 2024 Q1) if customer_type == 'VIP': return price * 0.85 return price # ❌ Malo — explica el QUÉ (el código ya lo dice) def calculate_discount(price, customer_type): # If customer is VIP, multiply by 0.85 if customer_type == 'VIP': return price * 0.85

7. Logging vs print()

import logging # Desarrollo / debugging: print() print(f"Debug: user={user_name}") # Eventos importantes y producción: logging logging.info("Application started") logging.warning("High memory usage detected") logging.error("Failed to connect to database") # Setup en main if __name__ == "__main__": logging.basicConfig( level=logging.INFO, format='%(asctime)s - %(levelname)s - %(message)s' )

8. config.py para constantes y configuración

# config.py DEBUG_MODE = True MAX_RETRIES = 3 TIMEOUT_SECONDS = 30 # Variables sensibles desde environment import os API_KEY = os.getenv('API_KEY', 'default-for-dev') DATABASE_URL = os.getenv('DATABASE_URL')

Las constantes van en config.py, no dispersas en el código. Las variables sensibles (API keys, passwords) siempre desde variables de entorno.
